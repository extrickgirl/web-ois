## 1. Цель и границы

### 1.1. Проблема

В настольном клубе сведения об играх и выдачах ведутся в таблице и переписке. Участник не видит, есть ли свободная коробка, и может приехать в клуб зря. Администратор вручную проверяет, кому выдали игру и когда её нужно вернуть; из-за этого одну коробку могут по ошибке обещать двум людям, а просроченные выдачи трудно находить. Руководитель клуба не знает точное количество доступных экземпляров.

### 1.2. Цель

Создать веб-систему, в которой участники видят каталог и отправляют заявки на получение игр, а библиотекарь оформляет выдачу и возврат конкретных коробок. Система должна не допускать двойной выдачи одного экземпляра и превышения лимита выдач участником.

### 1.3. Что входит

- Просмотр и поиск каталога игр, просмотр количества доступных экземпляров.
- Регистрация и вход участников, разграничение прав по ролям.
- Подача и отмена заявки на выдачу игры.
- Выдача конкретного экземпляра библиотекарем, указание срока возврата.
- Оформление возврата и просмотр истории выдач.
- Управление каталогом и экземплярами, просмотр просроченных выдач.

### 1.4. Что сознательно НЕ входит

| Не делаем | Почему |
|---|---|
| Онлайн-оплату и штрафы | В учебном клубе выдача бесплатная; финансовый модуль увеличит объём проекта. |
| Доставку игр на дом | Выдача и возврат выполняются лично в помещении клуба. |
| Бронирование игр на конкретное время | Заявка не закрепляет физическую коробку: её выбирает библиотекарь при выдаче. |
| Мобильное приложение | Адаптивного веб-интерфейса достаточно для первого релиза. |
| Интеграции с внешними каталогами игр | Данные вносятся самим клубом; интеграция не нужна для проверки основных сценариев. |

## 2. Роли

| Роль | Кто это | Что может |
|---|---|---|
| Участник (`member`) | Зарегистрированный посетитель клуба | Смотреть каталог и доступность; подавать и отменять **свои** заявки; смотреть свои выдачи и сроки возврата. |
| Библиотекарь (`librarian`) | Сотрудник, выдающий коробки | Смотреть заявки; выдавать свободный экземпляр; отмечать возврат; просматривать текущие и просроченные выдачи; видеть данные, необходимые для связи с участником. |
| Администратор (`admin`) | Ответственный за библиотеку | Всё, что библиотекарь; добавлять и редактировать игры и экземпляры; назначать роли; выводить экземпляры из фонда. |

Незарегистрированный посетитель может только просматривать каталог. Все операции изменения данных требуют входа в систему.

## 3. Сценарии

**С-1. Участник подаёт заявку на игру.**

1. Участник входит в систему и открывает каталог.
2. Выбирает игру и видит количество свободных экземпляров (это справочная информация, не гарантия выдачи).
3. Нажимает «Запросить игру».
4. Сервер проверяет, нет ли у участника незакрытой заявки на эту игру, и создаёт заявку со статусом `requested`.
5. Участник получает номер заявки и видит её в личном кабинете.

**С-2. Библиотекарь выдаёт коробку.**

1. Библиотекарь открывает список заявок со статусом `requested`.
2. Выбирает заявку и свободный экземпляр соответствующей игры.
3. Нажимает «Выдать»; сервер одновременно проверяет, что заявка ещё открыта, у участника меньше трёх действующих выдач и экземпляр свободен.
4. При успехе система фиксирует библиотекаря, дату выдачи, срок возврата через 14 календарных дней и статус `issued`; количество свободных экземпляров уменьшается на один.
5. Если проверка не пройдена, система ничего не выдаёт и показывает понятную ошибку.

**С-3. Участник возвращает игру.**

1. Участник приносит коробку библиотекарю.
2. Библиотекарь открывает действующую выдачу и сверяет идентификатор экземпляра.
3. Нажимает «Принять возврат».
4. Система фиксирует время возврата и переводит выдачу в статус `returned`.
5. Экземпляр снова становится доступным, если он не выведен из фонда.

**С-4. Участник отменяет заявку.**

1. Участник открывает свою заявку в статусе `requested`.
2. Нажимает «Отменить» и подтверждает действие.
3. Система переводит заявку в `cancelled`. Уже выданную игру отменить нельзя: её необходимо вернуть через библиотекаря.

**С-5. Администратор пополняет библиотеку.**

1. Администратор создаёт запись об игре или открывает существующую.
2. Добавляет экземпляр с уникальным инвентарным номером.
3. Система сохраняет экземпляр как доступный (`active`) и обновляет счётчик свободных коробок.

## 4. Бизнес-правила и функциональные требования

| № | Правило | Где обеспечивается |
|---|---|---|
| BR-1 | Один экземпляр игры может находиться не более чем в одной действующей выдаче (`issued`). | БД: частичный уникальный индекс по `copy_id` для строк со статусом `issued`; сервисный слой: атомарная операция выдачи. |
| BR-2 | У участника одновременно может быть не более **трёх** выдач со статусом `issued`. | Сервисный слой: подсчёт в транзакции с блокировкой строки пользователя; БД: транзакция. |
| BR-3 | Срок возврата устанавливается через **14 календарных дней** от момента выдачи. | Сервисный слой: расчёт `due_at` на сервере, а не на клиенте. |
| BR-4 | Выдавать и принимать возврат вправе только `librarian` и `admin`; управлять каталогом — только `admin`. | API: проверка авторизации и ролей до выполнения операции. |
| BR-5 | Участник вправе отменить только **свою** заявку со статусом `requested`. | API и сервисный слой: проверка владельца и статуса. |
| BR-6 | На одну игру у участника может быть только одна незакрытая заявка (`requested` или `issued`). | БД: частичный уникальный индекс по `(member_id, game_id)` для этих статусов; сервисный слой: проверка. |
| BR-7 | Выдача возможна только для экземпляра со статусом фонда `active`, относящегося к игре из заявки. | Сервисный слой: проверка `copy.game_id` и `copy.inventory_status`; БД: внешние ключи. |
| BR-8 | Состояние заявки меняется только по разрешённым переходам; повторная выдача или возврат завершённой выдачи запрещены. | Сервисный слой: проверка автомата состояний; API: ответ `409 Conflict`. |
| BR-9 | Просроченная выдача — это `issued`, для которой текущее время позже `due_at`; отдельного статуса `overdue` нет. | Сервисный слой: вычисляемый признак; фильтр списка выдач. |

### Одновременные запросы и защита от гонок

**Гонка по BR-1.** Два библиотекаря одновременно нажимают «Выдать» для одной физической коробки и разных заявок. Если оба сначала прочитают «свободна», обе выдачи могут пройти. Решение: выполнение операции в транзакции с блокировкой строки экземпляра (`SELECT ... FOR UPDATE`) и частичный уникальный индекс `UNIQUE(copy_id) WHERE status = 'issued'`. Успешной будет только одна выдача, вторая завершится `409 COPY_NOT_AVAILABLE` без частичных изменений.

**Гонка по BR-2.** У участника уже две выдачи. Два библиотекаря одновременно оформляют ему две новые, каждая операция отдельно видит число 2 и может увеличить его до 4. Решение: перед проверкой лимита транзакция блокирует строку участника (`SELECT ... FOR UPDATE`) и считает активные выдачи; после первой транзакции вторая увидит уже 3 и вернёт `409 LOAN_LIMIT_REACHED`.

**Гонка по BR-6.** Участник дважды отправляет запрос на одну игру почти одновременно. Ограничение уникальности по `(member_id, game_id)` для открытых заявок не позволит создать дубликаты; второй запрос вернёт `409 OPEN_REQUEST_EXISTS`.

Блокировки берутся в одном порядке: сначала строка участника, затем строка заявки, затем строка экземпляра. Это снижает риск взаимных блокировок. Все проверки и запись изменения выполняются в **одной транзакции**.

### Критерии приёмки

**AC-1 (BR-1, двойная выдача).** Дано: игра `game_id=10`, свободный экземпляр `copy_id=31`, две заявки (`loan_id=101` и `102`) разных участников в статусе `requested`. Действие: одновременно отправить два запроса `POST /api/loans/101/issue` и `POST /api/loans/102/issue` с `copy_id=31`. Ожидается: один ответ `200`, другой `409 COPY_NOT_AVAILABLE`; в БД ровно одна запись `issued` с `copy_id=31`.

**AC-2 (BR-2, лимит при гонке).** Дано: у участника две действующие выдачи и две заявки на разные игры, для которых есть свободные экземпляры. Действие: два библиотекаря одновременно оформляют обе заявки. Ожидается: один ответ `200`, один `409 LOAN_LIMIT_REACHED`; в БД ровно три выдачи участника в статусе `issued`.

**AC-3 (BR-5 и BR-8, отмена).** Дано: заявка `loan_id=103` создана участником А и имеет статус `requested`. Действие: участник Б делает `POST /api/loans/103/cancel`; затем участник А вызывает тот же метод. Ожидается: у Б `403 FORBIDDEN` и статус не меняется; у А `200`, статус становится `cancelled`; повторная отмена А возвращает `409 INVALID_STATE_TRANSITION`.

## 6. Модель данных

**User** — `id` (PK), `name`, `email` (UNIQUE), `password_hash`, `role` (`member` / `librarian` / `admin`), `created_at`.

**Game** — `id` (PK), `title`, `description`, `min_players`, `max_players`, `min_age`, `is_published`, `created_at`.

**Copy** — `id` (PK), `game_id` (FK → Game.id), `inventory_number` (UNIQUE), `inventory_status` (`active` / `retired`), `created_at`.

**Loan** — `id` (PK), `member_id` (FK → User.id), `game_id` (FK → Game.id), `copy_id` (NULL либо FK → Copy.id), `processed_by` (NULL либо FK → User.id), `status` (`requested` / `issued` / `returned` / `cancelled` / `rejected`), `requested_at`, `issued_at` (NULL), `due_at` (NULL), `returned_at` (NULL), `rejection_reason` (NULL).

**Связи:** один пользователь имеет много заявок/выдач; одна игра имеет много экземпляров и заявок; экземпляр участвует во многих выдачах **за всё время**, но максимум в одной действующей; библиотекарь может обработать много выдач.

**Ограничения БД:**

- `User.email` и `Copy.inventory_number` уникальны.
- `Game.min_players >= 1`, `Game.max_players >= Game.min_players`, `Game.min_age >= 0`.
- Для `Loan.status='issued'` обязательны `copy_id`, `issued_at`, `due_at`; для `returned` дополнительно `returned_at`.
- `Loan.copy_id` может быть `NULL` в `requested`, `rejected`, `cancelled`; у выданной/возвращённой игры он сохраняется для истории.
- Частичный уникальный индекс по `Loan.copy_id`, если `status='issued'`.
- Частичный уникальный индекс по `(Loan.member_id, Loan.game_id)`, если `status IN ('requested','issued')`.
- Соответствие экземпляра игре (`Copy.game_id = Loan.game_id`) проверяется сервисным слоем при выдаче.
- Физическое удаление `Game`, `Copy`, `User` при наличии связанных выдач запрещено; экземпляр выводится из фонда через `inventory_status='retired'` (только если он не выдан).

**Доступность игры:** количество `Copy` со статусом `active`, для которых не существует выдачи со статусом `issued`. Количество вычисляется запросом к БД, а не хранится отдельным изменяемым числом.

## 7. Архитектура

Архитектура — монолитное веб-приложение с отдельным фронтендом и REST API:

```text
Браузер участника / библиотекаря / администратора
                      |
                      v
            Frontend (React)
                      |
                 HTTPS / JSON
                      |
                      v
           Backend (FastAPI)
           |       |       |
        Auth    Loans    Catalog
           \       |       /
            Сервисный слой
                 |
           SQLAlchemy ORM
                 |
                 v
             PostgreSQL
```

- Frontend отвечает за страницы каталога, заявок и административной части.
- Backend проверяет токены, права, данные запроса и допустимость переходов состояний.
- Сервис выдач выполняет проверки и запись в одной транзакции PostgreSQL.
- БД хранит пользователей, каталог, экземпляры, историю заявок и выдач.
- Проверка прав и бизнес-правила не доверяются браузеру, даже если кнопки скрыты в интерфейсе.

## 8. Выбор стека

### 8.1. Критерии

Основные критерии: небольшой объём учебного проекта, понятный код, поддержка конкурентных транзакций, автоматическая документация API, простота локального запуска.

### ADR-1. Реляционная или документная БД

- **Контекст.** У одной игры несколько экземпляров, а каждый экземпляр не должен выдаваться двум людям одновременно. Нужны связи и ограничения целостности.
- **Варианты.** PostgreSQL — транзакции, внешние ключи, блокировки строк и частичные индексы; MongoDB — гибкая структура документов, но связи и обеспечение наших ограничений сложнее организовать.
- **Решение.** PostgreSQL.
- **Последствия (цена решения).** Нужны миграции схемы и понимание SQL-транзакций; изменение структуры данных менее свободное, чем в документной БД.

### ADR-2. Серверная платформа API

- **Контекст.** Требуется создать REST API с валидацией, ролевым доступом и Swagger-документацией в рамках учебного проекта.
- **Варианты.** FastAPI (Python) — аннотации типов, Pydantic, OpenAPI из коробки; Express (Node.js) — гибкий и популярный, но схему валидации и OpenAPI придётся настраивать дополнительно.
- **Решение.** FastAPI.
- **Последствия (цена решения).** Нужно следить за зависимостями Python и корректной работой синхронных операций с БД; производительность зависит от конфигурации приложения.

### ADR-3. Способ защиты от двойной выдачи

- **Контекст.** Одновременные запросы не должны приводить к выдаче одной коробки двум участникам или превышению лимита активных выдач.
- **Варианты.** Проверка доступности только в коде до записи — проста, но уязвима к гонкам; транзакции с блокировкой строк и уникальными ограничениями PostgreSQL — надёжнее, но сложнее в реализации и тестировании.
- **Решение.** Транзакции с блокировкой строк и ограничениями БД.
- **Последствия (цена решения).** При параллельной работе возможны ожидания блокировок; необходимо единообразие порядка блокировок, обработка конфликтов `409` и тесты гонок.

## 9. API

Все пути имеют префикс `/api`. Обмен — JSON в UTF-8; время — ISO 8601 в UTC (`2026-11-03T10:00:00Z`). Для защищённых методов используется заголовок `Authorization: Bearer <token>`. Списки возвращаются в виде `{"items": [...], "total": 0}`. Документация — `/docs`, спецификация — `/openapi.json`.

| Метод и путь | Кто вызывает | Что делает | Успех | Возможные ошибки |
|---|---|---|---|---|
| `POST /api/auth/register` | Гость | Регистрация участника | `201` | `409` email занят; `422` |
| `POST /api/auth/login` | Гость | Вход, получение токена | `200` | `401`; `422` |
| `GET /api/games` | Все | Каталог, поиск по `q` | `200` | `422` |
| `GET /api/games/{game_id}` | Все | Описание игры и число доступных коробок | `200` | `404`; `422` |
| `POST /api/games` | Администратор | Добавление игры | `201` | `401`; `403`; `422` |
| `POST /api/games/{game_id}/copies` | Администратор | Добавление экземпляра | `201` | `401`; `403`; `404`; `409`; `422` |
| `POST /api/loans` | Участник | Создать заявку (`game_id`) | `201` | `401`; `403`; `404`; `409`; `422` |
| `GET /api/loans/my` | Участник | Свои заявки и выдачи | `200` | `401`; `403` |
| `GET /api/loans` | Библиотекарь, администратор | Все заявки/выдачи; фильтры `status`, `overdue` | `200` | `401`; `403`; `422` |
| `POST /api/loans/{loan_id}/issue` | Библиотекарь, администратор | Выдать коробку (`copy_id`) | `200` | `401`; `403`; `404`; `409`; `422` |
| `POST /api/loans/{loan_id}/return` | Библиотекарь, администратор | Принять возврат | `200` | `401`; `403`; `404`; `409`; `422` |
| `POST /api/loans/{loan_id}/cancel` | Участник-владелец | Отменить открытую заявку | `200` | `401`; `403`; `404`; `409`; `422` |
| `POST /api/loans/{loan_id}/reject` | Библиотекарь, администратор | Отклонить открытую заявку с причиной | `200` | `401`; `403`; `404`; `409`; `422` |
| `PATCH /api/copies/{copy_id}` | Администратор | Изменить состояние экземпляра | `200` | `401`; `403`; `404`; `409`; `422` |

**Примеры запросов:**

```http
POST /api/loans
Authorization: Bearer <token>
Content-Type: application/json

{"game_id": 10}
```

Успешный ответ `201`:

```json
{"id": 101, "member_id": 7, "game_id": 10, "copy_id": null, "status": "requested", "requested_at": "2026-11-03T10:00:00Z"}
```

```http
POST /api/loans/101/issue
Authorization: Bearer <token>
Content-Type: application/json

{"copy_id": 31}
```

Успешный ответ `200`:

```json
{"id": 101, "game_id": 10, "copy_id": 31, "status": "issued", "issued_at": "2026-11-03T10:05:00Z", "due_at": "2026-11-17T10:05:00Z"}
```

**Единый формат ошибки** (в том числе для ошибок валидации):

```json
{
  "error": {
    "code": "COPY_NOT_AVAILABLE",
    "message": "Этот экземпляр уже выдан",
    "details": {}
  }
}
```

- `400` — некорректный запрос, не относящийся к валидации полей.
- `401` — пользователь не вошёл или токен недействителен (`UNAUTHORIZED`).
- `403` — нет необходимой роли или заявка принадлежит другому пользователю (`FORBIDDEN`).
- `404` — объект не найден (`NOT_FOUND`).
- `409` — конфликт с текущим состоянием (`COPY_NOT_AVAILABLE`, `LOAN_LIMIT_REACHED`, `OPEN_REQUEST_EXISTS`, `INVALID_STATE_TRANSITION`).
- `422` — неверный тип/значение параметра или тела запроса (`VALIDATION_ERROR`); подробности в `error.details`.
- `500` — внутренняя ошибка (`INTERNAL_ERROR`), без раскрытия трассировки клиенту.

Формат ошибок централизованно задаётся обработчиками исключений FastAPI, включая стандартные ошибки Pydantic, которые иначе имеют другой вид.

## 10. Окружения и развёртывание

| Окружение | Где | Данные | Особенности |
|---|---|---|---|
| Разработка | Ноутбук разработчика, Docker Compose | Тестовые игры и пользователи | Перезапуск кода при изменениях; подробные логи; локальная БД. |
| Тест | Отдельный контейнерный стенд | Искусственные наборы, в том числе данные для конкурентных тестов | Запуск автоматических и нагрузочных проверок; сброс БД между тестами. |
| Рабочее | Сервер клуба, HTTPS | Реальный каталог и выдачи | Миграции перед релизом, резервные копии раз в сутки, мониторинг; отключён режим отладки. |

Настройки передаются через переменные окружения: `DATABASE_URL`, `SECRET_KEY`, `ENV`, `CORS_ORIGINS`. Локальный `.env` исключён из Git; вместо него хранится `.env.example` без секретов. В рабочую среду нельзя переносить тестовые учётные записи, тестовую БД, включённую отладку и ключи из разработки. Токены передаются только по HTTPS.

## 11. Этапы работ

| Этап | Результат |
|---|---|
| 1. Проектирование | Согласовано ТЗ, построена схема сущностей и переходов состояний; выбран стек. |
| 2. Каталог и учёт экземпляров | Работает БД, миграции и API каталога; администратор добавляет игру и экземпляры, гости видят свободное количество. |
| 3. Пользователи и заявки | Работают регистрация, вход, роли, создание и отмена заявок; участник видит свои заявки. |
| 4. Выдача и возврат | Библиотекарь оформляет выдачу и возврат; работают ограничения BR-1–BR-9 и защита от гонок. |
| 5. Интерфейс и проверка | Реализован адаптивный интерфейс; проходят приёмочные, конкурентные и нагрузочные тесты; доступна Swagger-документация. |
| 6. Развёртывание | Система работает в рабочем окружении по HTTPS; настроены резервные копии и мониторинг. |

## 12. Глоссарий

| Термин | Значение |
|---|---|
| Игра (`Game`) | Название настольной игры и её общие характеристики; у одной игры может быть несколько коробок. |
| Экземпляр (`Copy`) | Конкретная физическая коробка с уникальным инвентарным номером. |
| Заявка (`requested`) | Запрос участника на игру, ещё не связанный с конкретной коробкой. |
| Выдача (`issued`) | Подтверждённая передача конкретного экземпляра участнику до определённого срока. |
| Просрочка | Выдача в статусе `issued`, у которой истёк срок `due_at`. |
| Бизнес-правило (BR) | Проверяемое ограничение или условие работы системы. |
| Критерий приёмки (AC) | Тест с исходными условиями, действием и ожидаемым результатом. |
| API | Программный интерфейс взаимодействия фронтенда и сервера. |
| ADR | Запись о техническом решении: контекст, варианты, выбор и последствия. |
| Транзакция | Группа операций БД, выполняемых атомарно: либо все изменения сохранены, либо ни одно. |
| MVP | Минимальная версия системы, реализующая основные пользовательские сценарии. |
